# クラス同時参加タイムアウトの調査と修正（2026-10-05）

## 報告と確認できた負荷要因

約20人のQR参加で時間切れが多発し、ホストの開始も時間切れになった。一部の生徒は時間切れ表示でも名簿には登録済みだった。

現行Gatewayはルーム単位で参加・状態取得・開始を直列化する。さらに、従来の通知fingerprintは参加者名簿・準備完了状況を全員向け制御通知に含めていたため、一人の参加が既存参加者全員の状態取得を誘発する。待機画面の初回3回取得や並行した再取得も負荷を増やす。旧Sites版はD1を直接呼ぶ構造で、このSupabase通知Gatewayはない。

10秒で端末が応答待ちを打ち切ってもサーバーの参加処理はロールバックされないため、名簿への登録と端末のエラー表示は両立する。本番ログを取得していないので、当日のタイムアウトの全原因を確定したものではない。

## 修正

- 名簿・準備完了の更新はホスト通知へ限定。フェーズ・設定・通知epochの変更は全員へ通知する。
- 待機時の3回時刻同期をやめ、COUNTDOWNで追加サンプルを取得する。
- 同時状態取得をまとめる。開始などの操作完了・制御通知が取得中に発生した場合は、取得後に新しい状態を必ず再取得する。
- 参加POSTの時間切れ等では、保存済みの同じトークンで登録状態を確認し、登録済みなら入室する。確認にも失敗した場合は元の参加要求を保持する。
- 参加枠・順序・二重処理防止・通知権限を守る排他制御は維持する。

## 検証

- `RUN_LOAD=1 node node_modules/vitest/vitest.mjs run`: 91ファイル・490テスト成功。42人の既存負荷テストを含む。
- 追加テストは修正前に失敗を確認。20人参加時の通知先、開始通知、取得中の状態無効化、参加応答消失後の復帰を検証。
- 型検査、productionビルド、Edgeバンドル生成、`git diff --check`成功。ビルドには500kB超chunkのサイズ警告が残る。
- Playwright MCPで独立した20ブラウザーコンテキストからQRが指す参加URLへ遷移し、名前入力・参加・ホスト開始を操作。20人が参加し、開始後は全員が第1問を表示。
- 一人の参加POST応答をサーバー処理後11.5秒遅延させた。POSTは一回だけで、時間切れ後に状態照会から入室できた。ホスト名簿は20人のまま。
- 390×844で20人の画面に横はみ出しなし。参加時のpageerrorなし。ホストAPIの参加者状態取得と開始は成功。
- テストAPIはPGliteを使用し、Google AuthとSupabase Realtimeは実サービスではない。Realtime WebSocketはテストAPIに実装がなく404となり、ブラウザー検証はHTTPフォールバックで実施。通知生成はPostgreSQLテストで検証した。
- 独立レビューで指摘された「取得中の古い状態に開始後の再取得が吸収される」問題は、後続取得と回帰テストを追加して解消。再レビューで追加指摘なし。

## 本番反映と残る確認

この節は参加対策の初回検証時点の記録。開始対策を含む最終検証・公開状況は `HOST_START_TIMEOUT_VERIFICATION.md` に記録する。DBマイグレーションは不要。

本番Supabaseの認証・接続プール・ロック待ち・通知遅延、学校回線や物理端末の性能は未測定。その後の開始対策で通知のclaim/send/ackを分離し、通知送信中のトランザクション保持を解消した。ローカル20人成功を、本番20人の性能保証とは扱わない。
